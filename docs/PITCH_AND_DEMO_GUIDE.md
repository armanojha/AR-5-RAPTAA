# Drishti: judge demonstration guide

## The one-line pitch

Drishti turns public satellite observations and official project reporting into an explainable answer to one operational question: **which corridor segment should be verified in the field first?**

## Demo path

1. Start on the React overview. It is backed by `frontend/public/drishti_bundle.json`, generated by the real-data pipeline.
2. Filter the three real corridors. Distinguish them from any clearly labelled synthetic portfolio placeholders.
3. Open a high-risk segment and show its temporal satellite chips, activity history, rainfall/observability context and evidence hash.
4. Open the evidence report or PDF. Explain that it is a field-verification request, not a finding of fault.
5. Show the evaluation, back-test, calibration and negative-control downloads. State their sample size and limitations exactly as generated—do not recite stale fixed metrics.
6. Demonstrate Track C separately as a protective extension; do not conflate it with construction-progress scoring.

## Technical claims that are safe to make

- Inputs are cached public-data windows from the project pipeline, including optical/SAR imagery and contextual layers where supplied.
- The system is segment-based and records low-observability locations as not assessable.
- Scores rank relative observable activity; they are not percentage-completion estimates.
- Evidence packages include provenance, cryptographic hashes and date-stamped visual chips.
- The integrated build covers three real corridors and retains a clear real/synthetic label in the frontend bundle.

## Claims that must be read from the current outputs

The following vary whenever the pipeline is rebuilt, so read them from the dashboard or exported JSON rather than memorising them:

- corridor and segment counts;
- alert count and severity;
- back-test lead time and detection rate;
- precision, recall, F1 and negative-control result;
- ML calibration and Track C event counts;
- financial or ROI estimates.

## Runbook

```powershell
# Rebuild all data, evidence and frontend assets
$env:PYTHONPATH = "src"
python -u -m drishti real-demo build --output-dir output\real_case

# Start the React interface (offline bundle mode)
Set-Location frontend
npm run dev

# Optional: serve the exact same bundle from the local API
Set-Location ..
$env:PYTHONPATH = "src"
python -m drishti alerts serve `
  --evidence-dir output\real_case\evidence `
  --bundle frontend\public\drishti_bundle.json
```

Set `VITE_DRISHTI_API_BASE=http://127.0.0.1:8765` in `frontend/.env.local` before starting Vite if API mode is required.

## Responsible-use close

“Drishti flags observable mismatches for independent field verification. It does not identify people, accuse contractors, decide payments, or replace engineering inspection.”
